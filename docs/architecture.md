# architecture

Four layers: a CLI shell, command orchestrators, agent-agnostic core primitives, and per-harness bridges. Skills and agent definitions are data (bundled `SKILL.md` / `src/agents/*.md` files), not code.

## Components

- **CLI (`src/cli.ts`)** — commander wiring. Parses args/flags and dispatches to a command function. No business logic.
- **Commands (`src/commands/`)** — one module per verb: `install`, `uninstall`, `update`, `set-mode`, `list`, `init`, `emit`, plus the active-skill verbs `track` / `status` / `reset` / `scan-prompt`. Orchestrate core + targets; hold no agent-specific knowledge.
- **Core (`src/core/`)** — agent-agnostic primitives:
  - `parse` — split frontmatter + body (gray-matter); `types` — shared types.
  - `frontmatter` / `template` — render a restricted YAML subset by hand; substitute `{{key}}` config placeholders.
  - `markers` — wrap / remove / extract `skillset:begin…end` blocks in shared files. `isAnchorMode` (in `types`) is the one place that says which modes are anchor modes — `always` and `context` — so a bridge never tests a mode name to recognise one.
  - `bundle` — enumerate and load bundled skills + their `templates/` and `assets/`, and resolve a declared sibling's source path (`skillSourcePath`).
  - `state` — read/write the install registry; match/upsert/remove records keyed by `(skill, agent, scope, mode, projectPath)`.
  - `declarations` — read and validate `skillset.config.json` (which skill belongs in which harness directory, which sibling files travel with it, and which fields a skill *requires* per harness), **plus the project's own `<root>/.skillset/config.json` when the run happens inside one** — additive, local entries only, with `projectPath` derived from the working directory and any problem reported against the path it came from. It then classifies every declared install — and each of its declared siblings — against both the state file and the disk: `in-sync` / `drifted` / `missing` / `adoptable` / `foreign` / `undeclared`. Reuses each target's `preview`, so the compared bytes come from the same renderer an install uses; siblings are compared as bytes against their bundle source, since a copy has no renderer. An install's reported status is the most urgent of its files'. `fieldSupport` is the capability half: it compares a skill's declared harness frontmatter (`targets.<agent>`, plus any top-level stray) and its `requires` entries against the target's declared record, returning warnings to report and errors that mean no write. `agentFieldSupport` is the same check for the agent kind, with one difference: a field a harness declares it *requires* — declared by the bridge, not the config — is an error when the artifact declares no value for it, because an omitted field can change what the artifact means (claude-code reads a missing `tools` line as every tool). `classifyInstall` dispatches on `kind`, so both kinds share the five statuses.
  - `active` — per-session active-skill store at `~/.skillset/active/<session-key>.json` (toggle/list helpers); session id or project-hash fallback. Backs `track`/`status` (see ADR 0002).
  - `statusline` — shared no-clobber add/remove for the singular `statusLine` settings field (Claude Code + Copilot CLI; see ADR 0003 / decision 9).
  - `locations` — skillset's own paths and nothing else: the state file, the suggestion queue, the repository's declarations file, and a project's `<root>/.skillset/config.json` (2e moved every harness layout into the bridges).
  - `fs` — atomic writes, presence checks, verbatim copies (`copyAtomic` / `copySiblings`). `body-size` — always-mode size warning. `prompt` / `diff` — interactive `update` divergence handling.
- **Bridges (`src/bridges/<harness>/`)** — one module per harness (`claude-code`, `pi`, `opencode`, `copilot`) implementing the `Bridge` interface (`install`, `uninstall`, `preview`, `artifactPath`, `skillDirectory`) plus `supportedModes` and a `frontmatter` capability record: the fields that harness can actually carry per mode (`expresses`), the consequence text for the ones it ignores, and the native command names an install must not shadow. A bridge that can also install agent definitions adds an `agents` capability — `path`, `install`, `uninstall`, `preview`, its own `expresses` record, and `required`, the fields whose absence changes the artifact's meaning. Each bridge owns that harness's locations, frontmatter projection, and shared-file anchors. Every bridge that writes a per-skill directory also copies the skill's declared sibling files into it, verbatim. Installing the `statusReader` skill (`skillset-status`) also drops that harness's tracking artifact — a `` !`skillset track` `` command trailer (Claude), an opencode plugin, a pi extension, or a Copilot CLI hook + statusLine (ADR 0003). `index.ts` is the registry — the only file that names a harness — and derives `BRIDGE_NAMES` and `AGENT_BRIDGE_NAMES` from what the bridges declare.
- **Skills bundle (`src/skills/<name>/`)** — canonical `SKILL.md` per skill, plus optional `_helpers/` (a declared sibling payload the skill's body invokes), `templates/` (e.g. convention's `docs/` scaffold) and `assets/` (foreign-runtime executable artifacts, e.g. `skillset-status/assets/{opencode-plugin.js, pi-extension.ts, copilot-hook.json}`). `scripts/copy-skills.mjs` copies the tree to `dist/skills/` at build so dev (tsx on `src/`) and prod (`dist/`) resolve the same layout; assets are excluded from `tsc`/`biome` (they target other runtimes).

## Data flow

- **install** — CLI → `install` loads the bundled skill (`bundle`), applies config, then for each agent calls `requireBridge(agent).install(ctx)`. The bridge renders harness-specific frontmatter and writes per-skill files and/or a marker block in an anchor file (`fs`, `markers`, `locations`), returning an `InstallRecord` that `state` persists to `state.json`. Where the mode writes a skill directory, the skill's declared siblings are copied verbatim beside `SKILL.md` and recorded per relative path. Before it writes, `fieldSupport` checks the skill's declared harness fields against the target's capability record: a field the harness cannot express is reported, and a `requires` entry it cannot render refuses the install with nothing written. A name that resolves to a bundled **agent** takes the same route through `bridge.agents`: the kind is set on the record (absent means skill), the mode is fixed at `auto`, and `agentFieldSupport` refuses a required field the artifact leaves undeclared.
- **update** — for each record, reload the skill and call `target.preview(ctx, record)` to compare on-disk bytes vs would-write bytes. Unchanged → re-install silently; diverged (local edits) → prompt / skip / overwrite per flags and TTY. A recorded sibling whose bytes left its source counts as divergence too, and is named in the prompt.
- **sync** — read `skillset.config.json`, classify every declared install (`declarations`), then act per status: install what is `missing`, record an `adoptable` artifact whose bytes already match without rewriting it, repair `drifted` from source while reporting the prior content, refuse a `foreign` file (exit non-zero), and report `undeclared` records (`--prune` removes them). Declared siblings are classified per file with the same vocabulary and reported individually. `--dry-run` classifies and writes nothing. Every write path renders through `applyConfigToSkill`, so a skill with `config:` placeholders compares against its substituted bytes. Before any of it, `fieldSupport` runs over every declaration: unsupported fields are reported, and a required field with no renderer exits 2 without writing — sync is all or nothing.
- **uninstall** — replay the record to remove exactly what was written: delete files (including recorded `assets`), strip the named marker block, drop the SessionStart hook entry, and remove the `statusLine` only if it's still ours (decision 9). Never touches unrecorded content.
- **track / status / reset** — `track <skill> [on|off]` toggles the per-session active set via `core/active`; the indiscriminate write surfaces (opencode plugin, pi extension, Copilot hook) pass `--known-only` so only installed skills are recorded. `status` prints the active set (reading the session id from a `--session` flag or a statusline stdin payload). `reset` clears the set when the agent compacts or clears the conversation — wired per agent: Claude `SessionStart` `clear|compact` hook, Copilot `preCompact` hook, the opencode plugin's `session.compacted` event, the pi extension's `session_compact`/`session_shutdown`. See ADR 0002.

## External dependencies

- Runtime: `commander` (CLI), `gray-matter` (frontmatter parse), `picocolors` (color).
- Dev: `vitest`, `@biomejs/biome`, `tsx`, `typescript`.
- Node ≥ 20. No runtime YAML serializer — `frontmatter.ts` renders the restricted subset we need (scalars + flat string arrays) by hand to keep the dependency surface small.
